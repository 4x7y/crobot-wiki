Arm and hand coordination: legacy example
=========================================

Source: :download:`examples/arm_hand_control/main.cpp <../../examples/arm_hand_control/main.cpp>`.
This is a historical experiment, not a working onboarding program for the
current API. It references ``SubChainController``, ``RBSubChain``, ``RBSubTree``,
the old two-argument ``MJSim`` constructor and callbacks accepting ``MJDataPtr``.
Those interfaces are absent from the current library headers.

Use :doc:`hybrid_control` for a current task-controller loop and
``examples/robot_ik/main.cpp`` for coordinated fingertip pose targets. The old
source can still explain the intended arm/palm/fingertip relationships, but
building it requires a code migration.

Migration map
-------------

.. list-table::
   :header-rows: 1

   * - Old example pattern
     - Current interface to investigate
   * - ``MJSim(filename, is_visualized)``
     - ``MJSim(filename)``, then ``show()`` or ``run()``.
   * - ``control(MJDataPtr)``
     - ``control()`` and ``MJRBTree`` live-state getters/setters.
   * - ``visualize(MJDataPtr, markers)``
     - ``visualize(MarkerManager&)``.
   * - ``set_qpos(data, ...)`` / ``forward_all(data)``
     - ``set_qpos_mj`` and an appropriate forward update.
   * - Subchain controller assembly
     - ``TaskSpaceController`` with explicit body/frame targets, or action
       orchestration; requires redesign rather than a mechanical rename.

An arm/hand assembly can have different position, velocity and actuator
layouts. Read named addresses from the loaded model and verify coupled joints.
A useful migration sequence is to reproduce the initial pose, track one arm
frame, add one fingertip, then combine targets. Draw the body-local offsets and
target frames at each stage. Keep physical-device integration separate until
the model and command semantics are established; see :doc:`hardware`.
