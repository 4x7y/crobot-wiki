State estimation and constrained filtering
==========================================

Link target: ``crobot-ekf``. Namespace: ``crobot::ekf``. This module supplies a
constrained Kalman-filter framework plus object dynamics and pose-tracking
formulations. It is not a sensor driver. See :doc:`api/ekf`.

Define the system
-----------------

Subclass ``KalmanFilterSystem`` with initial state/input, initial/reset
covariance, process and observation covariance, and constraint dimension.
Implement transition ``f(x, u, w)``, observation ``h(x, v)``, their Jacobians,
constraint residuals/Jacobians/tolerances, and the required constraint forms.
The system exposes dimensions through ``get_xdim``, ``get_udim``, ``get_wdim``,
``get_vdim`` and ``get_ydim``.

Write down the order, units and frame of every state and observation component
before assembling covariance matrices. Archived experiment configurations use
different state layouts; their covariance YAML files are not interchangeable.
``verify_diff`` compares model derivatives and is a useful first check for a
new formulation.

Run the estimator
-----------------

For an already constructed system:

.. code-block:: cpp

   crobot::ekf::KalmanFilterSolver filter(system, dt);
   if (filter.update(measurement, input)) {
     auto state = filter.get_state();
     auto variance = filter.get_variance();
     // Record or consume this estimate.
   }

The fragment needs ``ekf/kalman_filter_solver.hpp`` and dimensionally consistent
inputs. ``get_variance()`` returns the covariance diagonal;
``get_covariance()`` returns the full matrix. ``f`` describes a continuous-time
derivative, ``Q`` is the continuous-time process noise spectral density, and
``R`` is the discrete measurement covariance. Prediction uses the Euler state
transition ``F = I + dt*A`` and ``F*P*F.transpose() + dt*L*Q*L.transpose()``.
The measurement update solves the innovation system and uses Joseph covariance
form. Invalid dimensions/configuration throw ``std::invalid_argument``;
non-finite measurements, singular innovation, or constraint failure return
``false`` without changing the filter's state or covariance.

``reset()`` uses the model's ``reset_state`` hook (initial state by default).
Negative entries on the reset covariance diagonal retain the corresponding
covariance submatrix; cross terms with reset coordinates become zero.
``PoseTrackingSystem`` retains the estimated poses/contact parameters and zeros
the six object velocity components. Override ``innovation`` for measurements
with special residual rules, or ``get_ydim`` when measurement and noise
dimensions differ.

The constructor accepts a positive constraint-solver CPU-time limit and a
linearized-constraint option. With ``linearized_constraints=true``, bounded
Newton iterations project the posterior onto ``c(x)=0`` using minimum Euclidean
corrections, then project covariance onto the final tangent plane. The default
library option remains the existing IPOPT constrained-gain formulation. It
keeps the requested constraint tolerances and reports infeasibility, including
when a zero innovation cannot correct an inconsistent predicted state. It does
not silently relax tolerances. The example defaults to linearized projection.

Manipulation models and numerical support
-----------------------------------------

``PoseTrackingSystem`` combines ``ObjDynamics`` and ``StateObs`` with a dynamic
grasp. ``update_sensor_state`` supplies robot positions/velocities and contact
forces; ``unpack_x`` interprets its state layout, and ``update_obj_state`` updates
the associated object state. Keep its contact parameterization consistent with
the model in :doc:`kdl`.

Its state is object pose (7), object velocity (6), four surface parameters per
contact, then camera pose (7). Constraints are the object and camera quaternion
norms followed by five contact constraints per contact (three position, two
tangent/normal). Quaternion observations use normalized rotations with matching
Jacobians and sign-invariant innovations. This is the existing slow-manipulation
model: object acceleration is zero, with changes represented by process noise.

``LeastSquareSystem`` describes static parameters with zero dynamics and no
process noise or control. ``LeastSquareSolver`` reuses the same Kalman update
and accepts one measurement per call. ``CamTrackingSystem`` supplies the camera
calibration observation/constraint model formerly duplicated in the examples.
Use ``set_marker_transform`` for a known world marker pose, or the robot
constructor and ``update_sensor_state`` for the forearm marker site.

``PolynomialSystem``, ``PolynomialSolverNewtons`` and
``PolynomialSolverHomotopy`` provide nonlinear equation-solving support.
``KFConstrainedSystem`` and the ``LambdaVariable``/``LambdaConstraint``/
``LambdaCost`` helpers formulate the constrained update through optimization.

The consolidated ``examples/ekf`` executable exercises these public models.
See :doc:`examples` for modes, recorded data, and migration from the old projects.
