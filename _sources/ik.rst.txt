Inverse kinematics
==================

Link target: ``crobot-ik``. Namespace: ``crobot::ik``. Choose the solver based on
the constraints you need; :doc:`api/ik` lists all constraints, costs and variable
sets.

Jacobian IK: tracking frame targets
-----------------------------------

``JacobianIK`` iterates from supplied ``qpos`` and ``qvel``. Algorithms are
``TRANSPOSE``, ``SVD``, ``DAMPED_LEAST_SQUARE`` (default) and
``LEVENBERG_MARQUARDT``. Configure the iteration count and tolerance in the
constructor. LM also exposes ``set_lm_bias_damping`` and
``set_lm_step_tolerance``.

For an existing model with a body called ``tool``:

.. code-block:: cpp

   auto desired = crobot::kdl::WorldFrame::MakeShared(target_transform);
   crobot::ik::JacobianIK solver(
       robot, crobot::ik::JacobianIKAlgorithm::LEVENBERG_MARQUARDT,
       200, 1e-4);
   solver.add_target(desired, "tool");
   if (solver.solve(qpos, qvel)) {
     const auto solution = solver.get_qpos();
     // Apply or record solution here.
   }

This fragment needs ``ik/jacobian_ik.hpp`` and a valid model, target transform
and input state. ``add_target`` can specify a body-local offset and rotation.
``add_target_selected_dofs`` selects spatial directions; indices 0–2 are
rotational and 3–5 translational. ``add_rolling_target_selected_dofs`` uses a
rolling contact. ``fix_joint``, ``remove_fix_joint`` and ``fix_body`` constrain
motion. ``NullSpaceObj`` and its joint-limit, velocity, distance and quaternion
objectives provide secondary preferences.

The desired frame is shared with the solver: update it between solves to track
a moving target. Check the boolean result before using ``get_qpos()`` as an
accepted solution. A last iterate can exist even when the solve did not meet
tolerance. See ``test_jacobian_ik_lm.cpp`` for controlled cases and
``examples/robot_ik/main.cpp`` for two-fingertip replay in the viewer.

Generalized IK: explicit constraints
------------------------------------

``GeneralizedIK`` builds an optimization ``Problem`` with joint variables and
uses IPOPT. Construct it with a robot and the joint-limit setting, add named
constraints, set an initial configuration with ``set_init_qpos``, and call
``solve``. ``LoadFromFile`` and ``LoadFromYamlNode`` construct configured
problems; accepted YAML fields are defined in ``gik.cpp``.

.. list-table:: Constraint families
   :header-rows: 1

   * - Requirement
     - Interfaces / files
   * - Position or workspace bounds
     - ``add_position_target``, ``add_cartesian_target``,
       ``add_bounding_box_constraint``.
   * - Orientation or pointing
     - ``add_orientation_target``, ``add_orientation_vector_target``,
       ``add_aiming_target``, ``add_opposite_orientation_target``.
   * - Distance and joint relations
     - ``add_distance_target``, ``add_joint_position_constraint``,
       ``add_joint_coupling_constraint`` and ``fix_joint``.
   * - Contact geometry
     - Body, object, plane, point, surface, surface-point and surface-curve
       constraint classes in the ``cons_*`` headers.
   * - Quaternion normalization
     - ``add_unit_quaternion_constraint``.
   * - Preferred configuration/pose
     - ``add_potential_cost`` and the ``cost_*`` classes.

``solve(max_iter, max_time, verbose)`` has an outer retry loop: ``max_iter`` is
not simply IPOPT's iteration cap. The implementation configures IPOPT's own CPU
limit separately, so do not treat ``max_time`` as a hard real-time deadline.
``validate_constraints()`` helps inspect residuals. The public lookup method is
spelled ``get_constriant`` in this checkout; use that spelling in code.

Extending a problem
-------------------

``Variable`` and the ``vars_*`` classes connect joint, object-pose, curve and
surface parameters to optimization. ``Constraint`` and ``Cost`` bridge the
robot-specific formulations. ``PoseRefiner`` provides additional pose-refining
machinery. Follow the matching implementation when adding a new contact model:
geometry, variable bounds and Jacobians must describe the same parameterization.
See :doc:`optimization` for the sparse derivative contract.

If IK fails, first verify the target frame, local offset, selected directions,
joint limits, quaternion normalization and starting pose. Reduce the problem to
one target before adding contact and coupling constraints. IK alone does not
establish a collision-free path between configurations.

``PairCollisionConstraint`` is incomplete: its joint Jacobian is filled with
zeros, and its returned residual sign and bound direction are inconsistent with
its comments. Do not rely on this constraint alone for collision avoidance;
use explicit collision validation and verify a repaired formulation before use.
